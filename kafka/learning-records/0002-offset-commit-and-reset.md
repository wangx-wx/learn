# 第 2 课：位点提交机制已建立，业务场景已锁定

用户理解了「broker 存的是你**提交的**位点，不是你**处理到的**位置」这一区分，并掌握由此推出的两个结论：崩溃后从已提交位点恢复（→ 重复消费的根源），以及 `auto.offset.reset` 默认为 `latest` 而非 `earliest`（→ 「新消费者组读不到历史消息」的陷阱）。第 2 课 4 道检索题全部答对。

本课的教学入口是**用户自己提出的矛盾** —— 他在第 1 课回答里说「新版本的 Kafka 会自己建一个 topic 去保存 offset」，这与第 1 课的「位点在消费者手里」表面冲突。用他自己的疑问作为切入点，比预设题目更有效；这个矛盾即 `__consumer_offsets`（默认 50 分区 / 3 副本），它**不**推翻「位点在客户端」—— broker 只是被动保管箱。

## Evidence

- **检索练习**：4/4 全对（含直接考察该矛盾的题 3、以及「何时会重复消费」的题 4）
- **开放式检验（已做，结论修正了本记录的初稿）**：要求用「两个位置」框架解释「崩溃后为何重复消费」。用户**未能答出该框架** —— 回答描述了 Kafka 的整体架构（生产者 → Kafka → 消费者 → offset），但全程未出现「处理到哪」与「提交到哪」两个位置，也未描述崩溃瞬间两者各自的状态
- **两处具体偏差**：
  1. 回答以「**Kafka 是消息队列**」开头 —— 退回了第 1 课整课纠正的模型（术语表已把「消息队列」列为禁用语）
  2. 表述为「处理完成消息，会提交」—— 把处理与提交说成连续动作，漏掉默认 5 秒自动提交的窗口
- **关键区分**：同一次作答中，**第 2 题（CDC 场景下未提交位点导致重复消费）答对且推理正确**。说明模型**是存在的**，缺的是「被直接追问时把它显式调出来」的能力 —— 即 [[0001-log-model-established]] 里同样的模式：直觉具备，显式表述缺失
- **实操**：第 2 课实验待用户执行（命令已逐条加解释）

## 业务场景已锁定（重要）

用户明确了两条管道，**核心需求几乎相反** —— 这成为后续所有设计决策课的张力来源：

- **日志 / 埋点管道**：高吞吐、顺序要求弱、可容忍少量丢失与重复
- **数据库变更同步（CDC）**：吞吐中等、**同一行的变更必须保序**、**不可容忍丢失**、需幂等消费

已据此重写 `MISSION.md`。教学含义：不能再给「通用最佳实践」，必须让用户学会按需求权衡 —— 同一个参数（`acks`、分区数、key 选择）在两条管道里的正确答案不同。

## Implications

- **第 3 课定为「副本与 ISR」**（用户选择）：直接回应 CDC 的「不可容忍丢失」，讲清 `acks` / `min.insync.replicas` / HW 的边界。这是第 1 课预告过的主题
- **需要多 broker 集群**：副本实验单节点做不了。MISSION 里「用 Docker 搭多 broker 集群」这一目标可在本课顺带达成
- **术语表**：`位点`、`提交位点` 可从 `待验证` 升级；`__consumer_offsets`、`auto.offset.reset` 仍待第 3 课复检
- **检索设计（重要修正）**：连续两课出现同一模式 —— **选择题 4/4 全对，开放式提问却暴露缺口**（第 1 课是 topic/分区，第 2 课是「两个位置」框架）。结论：**选择题给出的信心信号不可靠**，四个选项并列时「认出来」远比「想出来」容易。
  后续检索必须**加大开放式生成题比重、减少选择题**，并要求用户用自己的话复述模型，而不是辨认选项。
- **教学风险**：用户的直觉理解领先于显式表述。若不刻意训练「把模型说出来」，排障时会依赖模式匹配而非推导 —— 遇到没见过的问题就无法迁移。**这是当前最值得投入的方向。**
