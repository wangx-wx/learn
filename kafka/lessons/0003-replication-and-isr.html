一、先说你对上一课三道题的回答

你的第 3 题答得相当好 —— 你自主推导出了生产者 / 存储 / 消费三个环节,这正好是 Kafka 可靠性的完整框架。这个框架是行业公认的划分方式,你等于自己复原了它。

但其中有一句话需要精确化。你写道:

「生产者生产消息的时候,需要保证将消息正常发送到 Kafka 中,可以同步发送」

「同步发送」是个含糊的说法 —— 同步等谁?等多久?这里其实有两个独立的参数在起作用,而它们的组合才决定结果。这正是本课的主题。

本课的核心命题

acks 决定「等几个副本」,min.insync.replicas 决定「低于几个副本就拒收」。只看 acks 会得出错误结论 —— 这正是最常见的一个认知陷阱。

二、副本与 ISR:一个动态的集合

一个分区有多个副本,其中一个是 leader,其余是 follower。所有的读写都走 leader,follower 的唯一工作是持续地复制 leader 的日志。

关键问题是:follower 们不一定都跟得上。有的可能网络卡了,有的可能进程卡了。于是 Kafka 需要区分两种 follower:

概念含义
ISR
in-sync replicas		 「跟得上 leader」的副本集合,包含 leader 自己。只有 ISR 里的副本,才有资格在 leader 挂掉后接班
LEO
log end offset		 某个副本的日志末端位置 —— 它自己写到哪了
HW
high watermark		 ISR 中最小的 LEO。这是消费者能看到的消息边界

「跟得上」的判定标准是时间,不是位置 —— 由 replica.lag.time.max.ms 控制,默认 30000(30 秒)。一个副本如果 30 秒内没能追上 leader 的 LEO,就被踢出 ISR。

动手玩一下。注意两件事:点击 broker 卡片可以让它挂掉或恢复;副本不会自动追上,必须点「让副本追上来」—— 这样你才能看见「leader 已写入、副本还没同步」那个危险窗口。

leader - · ISR - · HW 0 · 生产者已确认 0 条

请务必亲手做这个序列:

  1. 用 acks=1 发送一条 → 再点「让副本追上来」。注意消息早就被确认了,但 HW 才刚推进。
  2. 重置。把 broker-1 和 broker-2 点挂,只留 broker-0 → 用 acks=all、min.insync.replicas=2 发送。看它拒绝。
  3. 把 min.insync.replicas 改成 1,再发一次 → 这次接受了。同一个集群,同一个 acks,只因为 min.insync.replicas 不同,行为完全相反。

三、默认配置到底安不安全

这是本课最反直觉的一段。Kafka 4.3 的默认值是这样的(均来自官方文档):

参数默认值说明
acks(生产者)all等 ISR 全部副本确认
min.insync.replicas(broker/topic)1 ⚠️ISR 少于 1 个才拒收 —— 等于不设防
default.replication.factor(broker)1 ⚠️新建 topic 默认没有副本
enable.idempotence(生产者)true生产者侧去重,4.x 已默认开启
unclean.leader.election.enablefalse不允许非 ISR 副本当 leader(正确)

来源:生产者配置 · broker 配置(官方生成页,精确实时)

陷阱在这里

acks=all 看起来很强,但 min.insync.replicas=1 让它可以被架空:ISR 只剩 leader 自己时,acks=all 就退化成 acks=1 —— 等一个副本,就是等它自己。

更糟的是 default.replication.factor=1:你新建的 topic 根本没有副本。这种情况下,leader 所在的 broker 一挂,数据就没了,任何 acks 都救不了。

结论:默认配置给不了你 CDC 需要的持久性保证。必须显式设置。

那 CDC 管道该怎么配?

按你在使命里定的需求(不可容忍丢失),最小可用组合是:

# 建 topic 时:3 副本
--replication-factor 3

# topic 级别:要求至少 2 个副本在 ISR 里
min.insync.replicas=2

# 生产者:等所有 ISR 副本确认
acks=all

这三个一起用,才能保证「一条消息被确认时,至少存在于 2 个 broker 上」—— 挂掉任意 1 个都不丢。代价是:当可用副本少于 2 个时,写入会被拒绝(牺牲可用性换一致性)。这是你必须意识到的取舍,而不是 bug。

顺带回答你的第 1 题

你说「消费者处理完成消息,会提交消费完成的信号」—— 方向对,但漏了时机。第 2 课讲过:提交不是「处理完就自动发生」的,默认是每 5 秒一次的定时提交。所以崩溃那一刻,「处理到哪」和「提交到哪」之间几乎总有一段未被提交的消息 —— 这就是重复消费的窗口。这正是第 2 课那个模拟器演示的东西。

四、检索练习

前两题考本课,后两题考第 1、2 课 —— 混着考比只考新内容记得更牢。不要往回翻。

检索 1 / 4一个 broker 进程活着,但落后 leader 超过 30 秒。它的状态是?

「进程活着」和「在 ISR 里」是两件事。ISR 的判定标准是时间(replica.lag.time.max.ms,默认 30 秒),不是存活状态。

检索 2 / 4acks=all + min.insync.replicas=1,ISR 只剩 leader 时?

ISR 只剩 leader(1 个),不小于 min.insync.replicas=1,所以不拒收。此时 acks=all 退化为只等 leader 自己 —— 这正是默认配置的陷阱。

检索 3 / 4消费者组崩溃重启后,从哪个位置恢复消费?

第 2 课的内容。内存里的位置随进程消失,broker 里只留着你提交过的 —— 两者之间的消息会被重读,这是 at-least-once 的机制本身。

检索 4 / 4offset 编号的命名空间是什么?

第 1 课的内容,你在那里曾把它说成 topic。分区才是 offset 的命名空间 —— 3 个分区时 offset=0 同时存在三条。

五、动手:搭起 3 broker 集群,杀掉一个看看

副本实验单节点做不了 —— 必须有多个 broker 才有「副本」可言。本课顺带完成使命里「搭多 broker 集群」这个目标。

  1. 清理旧容器,避免端口冲突

    docker rm -f kafka

    前两课的单节点容器叫 kafka,先删掉。它的数据也会丢,没关系 —— 前两课的结论你已经验证过了。

  2. 启动 3 broker 集群

    docker compose -f docker-compose.cluster.yml up -d

    用工作区里准备好的编排文件(kafka/assets/docker-compose.cluster.yml)。-d 表示后台运行。如果你在 Mac 上,把文件拷到服务器再执行;或者直接把内容粘贴成一个文件。

    等约 30 秒,确认三个都起来了:

    docker compose -f docker-compose.cluster.yml ps

  3. 建一个 3 副本的 topic

    docker exec kafka-1 /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka-1:19092 \
  --create --topic cdc --partitions 3 \
  --replication-factor 3 --config min.insync.replicas=2

    注意三点:--replication-factor 3 让每个分区有 3 个副本;min.insync.replicas=2 是显式设置的(默认只有 1);bootstrap 地址用容器内部名 kafka-1:19092,因为命令是在容器里执行的。

  4. 看副本分布和 ISR

    docker exec kafka-1 /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka-1:19092 --describe --topic cdc

    输出里每个分区一行,重点看两列:Replicas 是副本分布在哪些 broker,Isr 是当前跟得上的副本。现在两者应该完全一样 —— 因为一切正常。记住这个基线,下一步它会变。

  5. 写入几条消息

    printf 'row-1\nrow-2\nrow-3\n' | docker exec -i kafka-1 \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka-1:19092 --topic cdc

    普通的写入。此刻 3 个副本都有数据。

  6. 杀掉一个 broker —— 关键一步

    docker stop kafka-3

    停掉 kafka-3,然后重新执行第 4 步的 --describe。盯住 Isr 那一列。

    你会看到什么

    凡是副本列表里含 3 的分区,它的 Isr 都少了一个 3 —— 变成两个。但 Replicas 那列没变,仍然是三个。

    这就是 ISR 的动态性:副本的分配是静态的,ISR 是动态的。kafka-3 还在副本名单里,只是暂时没资格。注意要等几秒让 30 秒的判定窗口过去,或者多刷几次。

  7. 再杀一个 —— 观察写入被拒绝

    docker stop kafka-2

    现在只剩 kafka-1 活着。含 1 的分区,ISR 只剩 1 个副本 —— 小于 min.insync.replicas=2。再试一次第 5 步的写入:

    printf 'should-fail\n' | docker exec -i kafka-1 \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka-1:19092 --topic cdc
    你刚刚证明了什么

    生产者会报错 —— 类似 NOT_ENOUGH_REPLICAS 或 NotEnoughReplicasException。消息被拒绝了,没有写进去。

    这不是故障,是设计意图:集群宁可让写入失败,也不接受一条无法保证冗余的消息。你的 CDC 管道要的正是这个行为 —— 失败可以被重试,静默丢数据不能。

  8. 把 broker 恢复,看 ISR 自己长回来

    docker start kafka-2 kafka-3

    等 30 秒左右,再 --describe 一次。Isr 会重新变回三个 —— 副本追上 leader 后自动重回 ISR。再写入一次,应该恢复正常。

    这一步也说明:broker 恢复后不是立刻回到 ISR,要先追上数据。这正是你在模拟器里点「让副本追上来」对应的真实过程。

先想再看

把 topic 的 min.insync.replicas 从 2 改成 1(--alter --add-config min.insync.replicas=1),然后再杀掉两个 broker、只留 kafka-1。这次写入会成功还是被拒绝?为什么?

再想一层:如果它成功了,这条消息此刻有几份副本?此时 kafka-1 挂掉,数据还在吗?

六、把这一课压缩成一句话

带走这一句

acks 决定等几个副本,min.insync.replicas 决定低于几个就拒收 —— 必须成对配置才有意义。默认值 acks=all + min.insync.replicas=1 + default.replication.factor=1 给不了持久性保证,CDC 场景必须显式设为 3 / 2 / all。

下次遇到「消息丢了」,按这个顺序查:topic 的 replication-factor 是多少?min.insync.replicas 是多少?生产者的 acks 是什么?三个都要问,只问一个会得出错误结论。
