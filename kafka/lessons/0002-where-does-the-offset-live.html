一、先说你在上一课撞出来的那个矛盾

第 1 课说:位点在消费者手里,boker 不知道你读到哪了。

而你在回答里提到:「新版本的 Kafka 会自己建一个 topic 去保存消息的 offset」。

这两句话看起来是打架的。但它们都对 —— 而且它们之所以能同时成立,正是理解 Kafka 消费语义的关键。这个内部 topic 叫 __consumer_offsets,默认 50 个分区、3 副本 (官方配置文档)。

解开矛盾的那句话是:

核心洞察

broker 存的是你主动提交上来的位点,不是你实际处理到的位置。它是个保管箱,不是监工 —— 它完全不知道你处理到哪了,只知道你上次汇报到哪了。

这个区别听起来很小,但它就是重复消费的全部根源。下面把它拆开看。

二、两个位置:处理到哪 vs 提交到哪

你的进程里其实有两个独立的「进度」:

处理到哪(processed)提交到哪(committed)
存在哪 你的进程内存里 broker 的 __consumer_offsets
怎么变 每处理一条就前进 你调用提交时才前进
进程崩溃后 丢了 还在
重启时用它吗 不用 —— 已经没了 用它,从这里继续

于是崩溃恢复的规则只有一句:从「提交到哪」继续,而不是从「处理到哪」继续。两者之间的那段消息,会被再处理一遍。

动手感受一下。下面模拟一个消费者:生产几条消息,处理几条,提交一次,然后崩溃重启 —— 注意崩溃后哪些格子会变回未处理。

日志末端 0 · 已处理到 0 · 已提交到 0 · 崩溃会重读 0 条

请务必亲手做一次这个序列:生产 4 条 → 处理 3 条 → 提交 → 再处理 1 条 → 崩溃并重启。最后一步之后,「已处理到」会从 4 退回到 3 —— 第 4 条(offset 3)回到了未处理状态。那条消息并没有消失,它只是又会被读一遍。

这就是 at-least-once 的字面含义

「至少一次」不是一个保证级别的名字,而是这个机制的直接后果:消息不会丢(提交了才前进),但可能重复(处理了没提交就崩)。Kafka 默认不提供「恰好一次」—— 想要它,得靠消费端幂等,或者生产者事务,那是后面的课。

三、默认配置里的一个陷阱

现在回到那个保管箱。有个场景你必须知道:

一个全新的消费者组,第一次来消费一个已经有数据的 topic —— 它从哪里开始读?

直觉会说「从头读吧」。但 Kafka 的默认答案不是这个。看官方文档里 auto.offset.reset 的默认值:

配置默认值含义
auto.offset.reset latest 没有已提交位点时,从日志末端开始
enable.auto.commit true 自动提交,默认开着
auto.commit.interval.ms 5000 每 5 秒提交一次 —— 不是处理完就提交

来源:Kafka 4.3 消费者配置(官方)

所以那个陷阱是:你新起一个消费者组去读一个已有 100 万条消息的 topic,默认一条都读不到 —— 因为它从末端开始等新消息。这正是很多「我的消费者怎么没反应」的真实原因。想要从头读,得显式设置 auto.offset.reset=earliest,或者在命令行加 --from-beginning。

顺带修正一个说法

第 1 课和第 1 课的速查卡里写的是 apache/kafka:3.9.0,你装的是 4.3.1。4.3.1 是当前最新版,CLI 工具名和路径(/opt/kafka/bin/)与 3.x 一致,本课命令照跑。唯一的重大差异是 4.0 起彻底移除了 ZooKeeper —— 只跑 KRaft。速查卡我已同步更新。

四、检索练习

不要往回翻。先凭记忆答,答完再看解析。

检索 1 / 4消费者进程崩溃后重启,它从哪里继续消费?

内存里的「处理到哪」随进程一起消失,broker 里只留着你提交过的位置。两者之间那段消息会被重读 —— 这就是重复消费的来源。

检索 2 / 4auto.offset.reset 默认是 latest,意味着什么?

注意这个配置只在「没有已提交位点」时才起作用 —— 它管的是「从哪开始」,不管「之后怎么走」。已有位点的组不受它影响。

检索 3 / 4broker 上的 __consumer_offsets 里存的是什么?

这是本课要解开的那对矛盾。broker 是被动接收提交的保管箱 —— 它存的是「你汇报到哪」,不是你「实际处理到哪」。所以「位点在客户端」这个结论依然成立。

检索 4 / 4下列哪种情况会导致同一条消息被处理两次?

崩溃点落在「已处理、未提交」这个窗口里,重启后就会重读。注意第三个选项:再平衡本身不会造成重复 —— 只有当它和「已处理未提交」叠加时才会。

五、动手:亲手制造一次重复消费,再重放一次

这一段把上面所有概念落到你的容器里。全部命令都在容器内执行,和上一课一样。

先对齐一下这些命令在干什么

你上一课说「对部分命令不太清楚」—— 这次每条命令后面我都写了它在做什么。看命令时先读那一句,再读命令本身,你会发现它们只是把参数翻译成动作而已。

  1. 确认容器还在

    docker ps --filter name=kafka --format '{{.Names}} {{.Status}}'

    应该看到 kafka Up ...。如果容器没了,用第 1 课那条 docker run 重新起一个。

  2. 建一个 3 分区的 topic

    docker exec kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --create --topic lesson2 --partitions 3 --replication-factor 1

    这次用 3 个分区,而不是上一课的 1 个 —— 目的是让你亲眼看到「offset 是分区内的编号」这件事。

  3. 写入带 key 的消息

    printf 'u1:a\nu2:b\nu1:c\nu3:d\nu2:e\nu1:f\n' | docker exec -i kafka \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic lesson2 \
  --property parse.key=true --property key.separator=:

    parse.key=true 让 producer 把冒号前的部分当 key。key 决定这条消息进哪个分区 —— 所以 u1 的三条会落到同一个分区。

  4. 看 offset 是怎么编号的(关键一步)

    docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic lesson2 \
  --from-beginning --property print.key=true \
  --property print.partition=true --property print.offset=true

    盯住输出里的 Partition 和 Offset 两列。你会看到 Partition:0 Offset:0 和 Partition:1 Offset:0 同时存在 —— 两个分区各自从 0 开始编号。这就是「offset 的命名空间是分区,不是 topic」的字面证据。上一课你把它说成了 topic,这里亲眼看一下差在哪。

  5. 用一个消费者组消费,然后观察位点

    docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic lesson2 \
  --group demo --from-beginning --max-messages 6

    这次加了 --group demo,所以它会把位点提交到 broker。消费完 6 条后进程退出。现在查这个组的位点:

    docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group demo

    看这张表的三列:CURRENT-OFFSET 是已提交位点,LOG-END-OFFSET 是日志末端,LAG 是两者之差 —— 积压量就是 LAG。这是你以后排障第一个要看的命令。

    如果 LAG 不是 0,别慌

    命令行消费者用的是自动提交(默认每 5 秒一次),而不是「处理完立刻提交」。如果你在 5 秒内就消费完 6 条并退出,最后那几条的位点可能还没来得及提交,于是 LAG 会剩下几。稍等几秒再查一次,或者干脆在消费时不加 --max-messages、让它多跑一会儿。这不影响下一步 —— 只要位点有提交,第 6 步的现象就会出现。

  6. 再消费一次 —— 这次应该什么都读不到

    docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic lesson2 \
  --group demo --from-beginning --max-messages 6

    你会看到它挂住不动。别急着 Ctrl-C,先想一秒:为什么这次 --from-beginning 不管用了?

    因为位点已经提交了

    --from-beginning 只在「没有已提交位点」时才有意义。这个组上次退出时已经提交到末端,所以它老老实实从末端开始等新消息。这恰好从反面证明了:提交的位点是真的被 broker 记住了。

  7. 重置位点,完成一次重放

    先 Ctrl-C 停掉上一步挂着的消费者(重置位点要求该组没有活跃消费者,否则报错)。然后:

    docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --group demo \
  --topic lesson2 --reset-offsets --to-earliest --execute

    --reset-offsets 就是「把保管箱里的位点改掉」,--to-earliest 表示改到最早,--execute 表示真的执行(不加它只预览)。这正是你在第 1 课里猜到的那个「可以重拨 offset 的命令」—— 你的推测是对的。

    现在把第 6 步的命令再跑一次,6 条消息又全部出现了。这就是重放。数据没动过,变的只是那个提交位点。

先想再看

把第 5 步的 --from-beginning 去掉(但保留 --group),换成一个新的组名 --group demo2 去消费 lesson2。它会读到什么?先写下预测,再执行验证。

六、把这一课压缩成一句话

带走这一句

broker 里的位点是你提交的,不是你处理到的 —— 两者的差就是崩溃后会重读的那一段。而「从哪开始」由 auto.offset.reset 决定,它的默认值是 latest,不是 earliest。

下次遇到「消费积压」,去查 --describe --group 的 LAG;遇到「消息重复」,去想崩溃点是否落在「已处理未提交」那个窗口里。这两类问题的排查方向,现在你都能自己推出来了。
