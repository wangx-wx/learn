Kafka 学习 · 第 4 课

「挂掉」不止一种

上一课你答对了「消息写进了 leader」——但 Kafka 的持久性，从来不是靠某台机器的磁盘

约 45 分钟 需要:第 3 课的 3 broker 集群 前置:第 3 课

本课结束后你能做到

  • 把「挂掉」说成一条谱线,而不是一个开关(进程 / 机器 / 磁盘 / 机房)
  • 解释 Kafka 为什么不靠本地磁盘保证持久,以及默认刷盘策略意味着什么
  • 判断一组「副本数 × 物理机数」的配置,能扛住哪一档失败

一、先回到你上一课的疑问

上一课的最后一问你答了「数据还在」,理由是「写入成功了所以会保存到日志」。你后来自己追问:为什么这个理解不完整?

因为那个问题问的其实是三层不同的事,而你的答案只覆盖了第一层。先把三层的标准答案摆出来 —— 在本课的场景里(acks=all + min.insync.replicas=1,ISR 只剩 leader):

问的是什么答案
① 消息写进 leader 的日志了吗?写进去了 ✓
② leader 这台机器挂了,还能读到吗?读不到了 ✗
③ leader 的磁盘坏了,还能恢复吗?彻底没了 ✗

你答对的是①。漏掉的是②③ —— 而 Kafka 的整个副本机制,恰恰是为②③设计的。你的盲区不在概念,在于「挂掉」这个词,你脑子里只有一档:容器被 kill。本课就把这一档拆成四档。

本课的核心命题

Kafka 的持久性保证,来自「别的机器上还有几份副本」,而不是「本机磁盘写没写」。任何一台机器,连同它的磁盘,都被假定随时可能整个消失。

二、失败是一条谱线,不是开关

「挂掉」在真实世界里是分层的。下面这四档,从左到右越来越狠,而每一档带走的副本数量不同:

档位发生了什么本机磁盘上的数据
① 进程挂broker 进程死了,机器和磁盘都好好的还在,重启就能读到
② 机器断电进程死,磁盘上的文件还在,但内存里的还没落盘大部分在,最新几条可能丢
③ 磁盘坏磁盘上的文件也没了没了
④ 机房整个没了整机房的机器一起下线没了

关键在于:第②档往下,本机的磁盘就不再可靠了。所以 Kafka 不把「持久」这件事寄托在任何一台机器上 —— 它靠的是同一份数据在别的机器上也有一份。

顺带拆一个常识:Kafka 默认不 fsync

你可能会想:「写进磁盘文件了,断电怎么还会丢?」因为在 Kafka 里,「写成功」不等于「已落盘」。Kafka 默认不是每条消息都强制刷盘,它把消息写进操作系统的 page cache,就认为「写好了」并返回。真正落到磁盘由操作系统择机完成。此时断电,page cache 里那部分就没了。

这个默认值不必背,去服务器上自己查 —— 顺便验证「不轻信记忆」这条原则:

docker exec kafka-1 /opt/kafka/bin/kafka-configs.sh \
  --bootstrap-server kafka-1:19092 \
  --entity-type brokers --entity-name 1 --describe --all | grep -i flush

看 log.flush.interval.messages 和 log.flush.interval.ms 的值。数字极大或为空,就意味着「几乎不主动刷盘」。这正是为什么持久性必须靠副本份数,而不是靠单机磁盘。

三、亲手算一算:你这套配置能扛住哪一档?

下面这个小工具把「副本数」和「物理机台数」两个变量放在一起。切换它们,看每种失败下数据还在不在 —— 特别注意你现在的实验环境(1 台机器)和生产环境(3 台机器)的区别。

    请务必亲手做这两组对比:

    1. 副本数 3、物理机 3 台 → 记住「机器挂了还剩几份」这个数。
    2. 副本数 3、物理机改成 1 台 → 看第②③④档变成什么颜色。这就是你 Docker 里那套集群的真实处境。
    必须诚实告诉你的一件事

    你那 3 个 broker 跑在同一个 Docker 里,也就是同一台物理机上。所以它只能真实演示第①档(进程挂);②③④档它演不了 —— 物理机一挂,3 个容器一起没。

    这不是实验的缺陷,这就是为什么单机 Docker 集群永远只是沙盘:它让你练「进程挂了 ISR 怎么变」,但练不了「机器报废」。生产环境里那 3 个副本,是在3 台不同的物理机上,才是真有意义的三份。

    四、动手:亲手区分「进程挂」和「机器报废」

    这四步会在你的集群上跑。注意前两步和后两步结果完全不同 —— 那正是本课要你亲眼看见的。

    1. 先记下基线

      docker exec kafka-1 /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka-1:19092 --describe --topic cdc

      如果上一课的 cdc topic 还在,直接看。不在就先按第 3 课第 3 步重建一个。

    2. 进程挂 —— docker stop

      docker stop kafka-3
docker start kafka-3

      停掉再启动。docker stop 只是让进程退出 —— 容器的可写层(里面的 /tmp/kraft-combined-logs)原封不动。所以 kafka-3 起来后数据还在,它只是把落后的那几条追回来,重新回到 ISR。

      你会看到什么

      等 30 秒左右再 --describe,Isr 自己长回三个。这是「机器重启」 —— 第①档,数据没丢。

    3. 机器报废 —— 删容器重建

      docker rm -f kafka-3
docker compose -f docker-compose.cluster.yml up -d kafka-3

      docker rm 会把容器的可写层一起删掉。重建出来的 kafka-3 是一台空机器 —— 它没有任何历史数据,必须从 leader 那里全量同步才能重新回到 ISR。

      你刚刚证明了什么

      同一个「kafka-3 下线再上线」,stop/start 保留了数据,rm/up 没有。「机器挂了」这四个字,可以是两件完全不同的事。

      注意:这一步之所以没演成灾难,是因为还有 kafka-1、kafka-2 这两份副本在。如果只有 1 份副本,kafka-3 这条命令下去,数据就真的没了。

    4. 把整台「机器」端掉(可选,谨慎)

      docker compose -f docker-compose.cluster.yml down

      down 会删除全部容器。因为没有声明 volumes,所有数据一并消失。这就是第④档的迷你版 —— 你那台物理机就是它们的「机房」。

      再 up -d 起来时,集群是全新的,cdc topic 需要重建。亲手体验一下「数据真的没了」是什么感觉 —— 在沙盘上体验,好过在生产上体验。

    先想再看

    生产环境:3 台物理机,每个分区 3 副本,min.insync.replicas=2。现在整台机器 2 报废(连同它的磁盘)。数据还在吗?写入会怎样?恢复要等多久?

    再想一层:如果 min.insync.replicas=1 而不是 2,同一场事故下,写入会不会已经悄悄接受了新消息?那些消息现在在哪?

    五、检索练习

    前两题考本课,后两题考第 3 课。按老规矩 —— 先用自己的话在心里答一遍,再展开对照。

    检索 1 / 4「Kafka 默认不每条 fsync」—— 那么消息的持久性最终由什么保证?

    持久性来自「别的机器上还有一份」,不是来自本机磁盘。这条一旦记住,Kafka 的所有副本设计就都顺了。

    检索 2 / 43 副本全部分布在同一台物理机上,等效于几份冗余?

    对进程级失败它像 3 份;对机器级失败它只有 1 份。而 CDC 要防的是机器级 —— 所以「副本数」之外,还必须问「分布在哪几台机器」。

    检索 3 / 4(开放式)· 用你自己的话:为什么「写入成功」不等于「数据安全」?

    参考答案的骨架:「写入成功」只说明消息进了当时存在的那些副本的日志。它有几份安全,取决于那一刻有几个副本收到了。在 min.insync.replicas=1、ISR 只剩 leader 时,「成功」只意味着 1 份,leader 机器一挂就没了 —— 而生产者已经收到了「成功」。所以正确说法是:写成功 = 进了几个副本;安全 = 那几个副本是否互相独立。

    如果你说到了「份数」和「独立分布」这两点,就算过关。

    检索 4 / 4(开放式,第 3 课复检)· 一个 broker 进程活着但落后超过 30 秒,它算不算「同步副本」?

    不算。ISR 的判定标准是时间(replica.lag.time.max.ms),不是存活。「进程活着」和「在 ISR 里」是两件事。

    追问一句:这话和本课的命题像不像?—— 本课是「进程活着 ≠ 机器活着」,第 3 课是「进程活着 ≠ 在 ISR 里」。同构:都是提醒你「一个状态标签,盖不住底下的多种真相」。

    六、把这一课压缩成一句话

    带走这一句

    问「数据会不会丢」时,不要问「写成功了吗」,要问:「这一刻有几份副本,它们分布在几台独立机器上?」 —— 进程挂、机器挂、磁盘坏、机房没,只有后者才需要靠「跨机器」来兜底。

    这也解释了你使命里两条管道的分野:日志管道可以接受第①档就够(丢几条无所谓);CDC 管道必须扛到第③④档,所以副本数 × 物理机分布,才是它的安全底线。
