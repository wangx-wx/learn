Kafka 学习 · 第 1 课

Kafka 不是队列，是日志

一个概念上的重新分类，能解释掉你过去所有「为什么 Kafka 要这样设计」的疑惑

约 60 分钟 需要：一台可跑 Docker 的服务器 前置：用过 Producer / Consumer API

本课结束后你能做到

  • 说清「队列」和「日志」在消息消费后的根本差异，以及这个差异带来的 4 个后果
  • 解释为什么 Kafka 的位点（offset）由消费者维护，而不是 broker
  • 在服务器上跑通一次实验：同一条消息被消费两次 —— 亲手证明它没有被删除
  • 知道「分区内有序」这句话的确切边界在哪里

一、你已经会用的那个 API，藏着一个误解

你用 @KafkaListener 收过消息，也用 KafkaTemplate 发过消息。现在请你凭直觉回答一个问题：

一条消息被消费者处理之后，它还在 Kafka 里吗？

如果你的直觉是「应该没了吧，消息队列不就是这样」—— 这个直觉来自 RabbitMQ、ActiveMQ、JMS 那一脉。在那个世界里它是对的。但在 Kafka 里，它是错的，而且这个错误会连锁地让你看不懂后面几乎所有设计。

二、队列 vs 日志：一个关键动作的差别

两种模型在「读」这个动作上，语义完全不同。

队列（Queue）日志（Log）
读的本质 取走（destructive read） 移动一个指针（non-destructive read）
读完之后 消息从存储中移除 消息原封不动留在原地
谁能再读一次 没有人 —— 它没了 任何消费者，只要把指针移回去
多个消费者 竞争同一条消息（分摊工作） 各自持有一份独立的指针（各自读全量）
消息何时消失 被消费时 超过保留期限（时间或体积）时

亲手操作一下这个差别。下面是一个日志，每条消息有一个永久的位置编号，叫作 offset。试着「追加」几条，然后「读取」—— 注意读取只是把红色指针往后挪，格子本身没有任何变化。

日志长度 0 条 · 下一条待读 offset 0 · 本消费者已读 0 条

追加到第 6 条、读到第 4 条，然后停下来看一眼：日志长度是 6，指针在 4。这 6 条消息一条都没少。在真实 Kafka 里，这个「指针」就是位点（offset），而它保存在消费者这一侧，不在 broker 上。

核心洞察

Kafka 的「消费」不是一个改变数据的动作，而是一个只读的游标移动。数据一旦写入就不可变，能变的只有你读到哪里。这一个事实，单独就解释了 Kafka 大部分的「奇怪设计」。

三、这个差别带来的四个后果

下面每一条，都是「日志」这个模型直接推出来的。读的时候注意体会：它们不是四个独立特性，是同一个事实的四个侧面。

1. 重放是免费的

既然消息没被删，那么「把昨天的事件重新处理一遍」就不需要生产者重发。把位点移回去就行。这解锁了一整类能力：新增一个消费者时回填历史、发现 bug 后重算结果、给新业务线补一份数据。

2. 位点在消费者手里

broker 不知道你读到哪了 —— 它只负责存。这是为什么提交位点是客户端的行为，也是为什么「重复消费」在 Kafka 里是常态而非故障：你的进程在读完之后、提交位点之前崩溃，重启后就会从上一个已提交的位点重读。这个语义叫 at-least-once（至少一次）。

常见误解

「Kafka 保证消息不丢不重」—— 不准确。默认配置下 Kafka 保证的是不丢，但可能重复。要做到不重，需要额外的机制（幂等生产者、事务、或者消费端自己幂等），那是后面的课。

3. 顺序只在分区内保证

日志是分区（partition）粒度的：一个 topic 由多个分区组成，每个分区是一条独立的日志。offset 只在单个分区内有意义，跨分区之间没有任何顺序关系。

这直接推出一条设计原则：需要保序的消息必须落在同一个分区，而分区选择通常由消息的 key 决定。反过来，分区又是并行度的单位 —— 一个分区同时只能被同一个消费者组里的一个消费者读。于是「顺序」和「并行」成为一对必须显式权衡的力量。

4. 保留期与消费无关

消息消失的条件是时间到了（默认 7 天）或体积超了，跟你读没读完全没关系。所以「消费太慢导致消息被删」是可能的 —— 但原因不是你没读，而是你读得太慢、超过了保留期。这是两个不同的因果，排障时的方向完全不同。

四、检索练习

不要往回翻。先凭记忆答，答完再看解析。想不起来是好事 —— 那正是记忆在生长的地方。

检索 1 / 4一条消息被成功消费之后，它在 Kafka 中的状态是？

消费只移动游标，不改数据；而游标存在消费者侧，所以 broker 并不知道你读到哪。这两点是绑在一起的 —— 正因为消息还在，位点才有「移回去」的意义。

检索 2 / 4Kafka 在什么范围内保证消息的先后顺序？

offset 是分区内的序号，所以顺序保证的边界就是分区边界。推论：要保序就得让相关消息进同一分区（通常靠 key），代价是牺牲这部分消息的并行度。

检索 3 / 4要把昨天的消息重新处理一遍，最直接的做法是？

消息还在，所以重放是「读」侧的事，与生产者和副本都无关。这也是为什么 Kafka 常被当作「可重放的事件源」，而不只是一个传输管道。

检索 4 / 4把一个 topic 的分区数从 3 增加到 6，直接影响是？

分区是并行单位，所以分区数决定了一个消费者组能并行到几个人。但分区数变多，原本「同一分区所以有序」的消息可能被拆散 —— 而且 Kafka 不支持减少分区，所以这个决定代价很高。

五、动手验证：让同一条消息被读两次

上面的道理你都懂了。但「懂」和「亲眼见过」在记忆里是两种强度。这一段用大约 20 分钟，在你自己的服务器上把这个结论砸实。

整段实验只需要 Docker，不需要本机装 Kafka。所有 kafka-*.sh 命令都通过 docker exec 在容器里执行 —— 这样能绕开 advertised.listeners 那个经典的连接坑，让第一次跑通的成功率最高。

关于版本

下面用 apache/kafka:3.9.0（官方镜像，KRaft 模式，不需要 ZooKeeper）。如果拉取失败或启动报错，把报错贴给我，我帮你换成 docker compose 的写法 —— 那条路更啰嗦但更可控。

  1. 启动一个单节点 broker

    docker run -d --name kafka -p 9092:9092 apache/kafka:3.9.0

    等大约 15 秒，然后确认它真的起来了：

    docker logs kafka | tail -5

    看到 Kafka Server started 或类似字样就说明可以了。

  2. 建一个只有 1 个分区的 topic

    docker exec kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --create --topic lesson1 --partitions 1 --replication-factor 1

    只建 1 个分区是有意的：这样「顺序」这件事不会被并行干扰，你看到的顺序就是日志的顺序。

  3. 写入 5 条消息

    printf 'msg-1\nmsg-2\nmsg-3\nmsg-4\nmsg-5\n' | docker exec -i kafka \
  /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic lesson1

    生产者写完了。此刻消息已经落在磁盘上。

  4. 第一次消费 —— 顺便把 offset 打出来

    docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic lesson1 \
  --from-beginning --max-messages 5 \
  --property print.offset=true --property print.partition=true

    你会看到 5 条消息，每条前面带着分区号和 offset：Partition:0 Offset:0 msg-1 这样。看完 Offset 这一列 —— 它是消息的永久地址，不是序号。

  5. 关键一步：把完全相同的命令再跑一遍

    docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic lesson1 \
  --from-beginning --max-messages 5 \
  --property print.offset=true --property print.partition=true
    你刚刚证明了什么

    消息全都还在，offset 也一模一样。消费没有删除任何东西。如果这是 RabbitMQ，第二次执行会一直挂着等新消息 —— 因为旧的已经没了。这就是「队列」和「日志」在行为上最直观的分界。

  6. 看看这个日志的物理边界

    docker exec kafka /opt/kafka/bin/kafka-log-dirs.sh \
  --bootstrap-server localhost:9092 --topic-list lesson1 --describe

    输出里的 offsetLag 和 size 就是分区日志的真实状态。留意 size —— 这是消息在磁盘上占的地方，它不会因为你读过而变小。

先想再看

在你执行第 5 步之前，先写下你的预测：第二条命令的输出，会和第一条完全一样吗？如果不一样，你预期哪里不同？

实验做完之后

容器可以留着（后面的课还要用）。要清理就 docker rm -f kafka。注意：这个单节点配置副本数为 1，没有任何冗余，只适合学习，不能用于生产 —— 副本与 ISR 是第 3 课的主题。

六、把这一课压缩成一句话

带走这一句

Kafka 的消费是移动一个只读游标，不是取走数据 —— 由此推出：可重放、位点在客户端、分区内有序、保留期与消费无关。

下次当你遇到「消息重复了」「消费积压了」「顺序乱了」这类问题时，先回到这句话：它在告诉你，问题几乎总在游标那一侧，而不是数据那一侧。
